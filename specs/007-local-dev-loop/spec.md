## User Scenarios & Testing

### User Story 1 — Начать локальную работу и увидеть правку (Priority: P1)

Разработчик одной командой запускает локальный стенд, получает ссылку и работает с настоящим приложением. Изменения интерфейса и серверного кода применяются автоматически без ручной пересборки поставки.

**Why this priority**: Это основной результат перехода с серверной выкладки на localhost.

**Independent Test**: Запустить стенд, открыть интерфейс, получить реальные данные bootstrap и по одной обратимой правке интерфейса и серверного кода увидеть автоматическое обновление.

**Acceptance Scenarios**:

1. **Given** зависимости подготовлены и локальные адреса свободны, **When** разработчик запускает стенд, **Then** команда сообщает ссылку, интерфейс открывается и получает данные локального приложения.
2. **Given** стенд работает, **When** сохранена правка интерфейса или серверного кода, **Then** новое поведение становится доступным без повторной команды запуска.
3. **Given** обязательная зависимость или локальный адрес недоступны, **When** запрошен запуск, **Then** причина понятна из сообщения, ложная готовность не объявляется.

### User Story 2 — Остановить и продолжить без потери данных (Priority: P1)

Разработчик видит состояние и журналы стенда, останавливает его одной командой и позднее продолжает с теми же локальными документами и отчётами. Другие окружения продолжают работать.

**Why this priority**: Простой запуск полезен только при предсказуемой остановке и сохранении работы.

**Independent Test**: Создать синтетические локальные данные, выполнить stop/start, проверить сохранность; отдельно проверить повторный запуск, занятой адрес, устаревшую запись процесса и отсутствие остановки чужого процесса.

**Acceptance Scenarios**:

1. **Given** локальные данные сохранены, **When** выполнены остановка и повторный запуск, **Then** документы и сохранённые отчёты остаются доступными.
2. **Given** стенд уже работает, **When** повторно запрошен запуск, **Then** второй комплект сервисов не появляется, команда показывает текущее состояние.
3. **Given** параллельно работают другие локальные окружения, **When** этот стенд остановлен или его запуск завершился ошибкой, **Then** чужие процессы и данные остаются нетронутыми.
4. **Given** информация о процессе устарела, **When** выполнена остановка, **Then** чужой процесс с повторно использованным идентификатором не завершается.
5. **Given** стенд работает или завершился с ошибкой, **When** запрошены состояние и журналы, **Then** разработчик видит текущие сервисы и причину сбоя без раскрытия credentials.

### User Story 3 — Работать с актуальным состоянием внешней модели (Priority: P2)

Разработчик использует OpenAI по умолчанию или выбирает существующий профиль Kimi K2. Доступность профиля проверяется при запуске и регулярно обновляется, чтобы работающий стенд не терял модель из-за истечения срока проверки.

**Why this priority**: Локальный интерфейс должен отражать фактическую доступность существующей интеграции.

**Independent Test**: Получить начальное состояние профиля, дождаться следующего обновления и проверить продолжение работы сервисов при ошибке проверки поставщика.

**Acceptance Scenarios**:

1. **Given** данные стенда подготовлены, **When** выполнен запуск, **Then** первая проверка доступности профиля выполнена без генерации текста.
2. **Given** стенд продолжает работать, **When** проходит очередной интервал 60 секунд, **Then** выполняется следующая проверка доступности.
3. **Given** поставщик недоступен, **When** проверка завершается ошибкой, **Then** профиль показывает недоступность, причина записана в журнал, а локальные сервисы продолжают работать.
4. **Given** настроен существующий credential, **When** выполняются проверки, **Then** секрет используется из приватного файла и отсутствует в выводе команд, аргументах процессов и Git.

### Edge Cases

- Занят адрес, отсутствует локальная зависимость, файл конфигурации или credential: понятная ошибка без вмешательства в соседние окружения.
- Частичный запуск, одновременный или повторный start/stop, устаревшая запись процесса: управляются только доказуемо принадлежащие стенду процессы.
- Перезапуск серверного кода: старый экземпляр освобождает ресурсы до готовности нового; после обновления приложение остаётся работоспособным.
- Ошибка или задержка поставщика: проверки не перекрываются бесконтрольно и не останавливают локальную работу.
- Остановка: журналы и артефакты сохраняются в приватном локальном состоянии; удаление данных требует отдельного действия вне этого среза.

## Requirements

### Functional Requirements

- **FR-001**: Предоставить простые команды запуска, остановки, просмотра состояния и журналов; успешный запуск сообщает локальную ссылку. Проверка: US1.1, US2.5.
- **FR-002**: Правки интерфейса и серверного кода применяются автоматически во время работы стенда. Проверка: US1.2.
- **FR-003**: Интерфейс обращается к настоящему локальному приложению с отдельными сохраняемыми данными и существующими ограничениями runtime. Проверка: US1.1, US2.1.
- **FR-004**: Проверять обязательные условия запуска, предотвращать дублирование и корректно очищать собственный частичный запуск. Проверка: US1.3, US2.2–4.
- **FR-005**: Остановка затрагивает только ресурсы этого dev-стенда и сохраняет локальные документы, отчёты и журналы. Проверка: US2.1, US2.3–4.
- **FR-006**: Использовать OpenAI по умолчанию с явным выбором Kimi K2 и существующий навык ревью `review-data-spec` версии 1.0.1; credential получать из приватного файла без раскрытия значения. Исходная проверка Kimi: US3.1, US3.4 и проверка выбранного навыка; OpenAI реальным запросом не проверен.
- **FR-007**: Выполнить первую негенеративную проверку доступности после подготовки данных и повторять её каждые 60 секунд во время работы стенда. Проверка: US3.1–2.
- **FR-008**: Ошибка поставщика отражается как недоступность профиля и запись журнала, не завершает dev-сервисы. Проверка: US3.3.
- **FR-009**: Короткая инструкция запуска и фактические результаты проверок доступны из карты технического репозитория. Проверка: переходы по ссылкам из README.

### Key Entities

Новых доменных сущностей нет. Существующие основные документы, запуски и неизменяемые отчёты остаются в отдельном локальном хранилище. Служебное состояние launcher описано в [плане](plan.md).

## Success Criteria

### Measurable Outcomes

- **SC-001**: Одна команда запуска даёт рабочую локальную ссылку; интерфейс успешно получает реальные данные приложения.
- **SC-002**: Две обратимые правки — одна интерфейса и одна серверной логики — применяются без ручного перезапуска стенда.
- **SC-003**: После одного полного stop/start сохранённые синтетические данные доступны; чужие окружения сохранили исходное состояние.
- **SC-004**: Начальная и как минимум одна очередная проверка обновляют состояние профиля; имитация ошибки поставщика не завершает сервисы.
- **SC-005**: Проверки lifecycle подтверждают отсутствие дубликатов запуска и остановки чужих процессов при конфликте адресов, устаревшем состоянии и частичной ошибке.

## Assumptions

- Пользователь разрешил реализацию и использование уже сохранённого credential; этот срез рассчитан на одного локального разработчика.
- Версии зависимостей зафиксированы существующими lock-файлами; обычная правка кода не требует пересборки поставки.
- Внешние OpenAI и Kimi K2 требуют сети; негенеративная availability не доказывает качество ревью или успешную генерацию.
- Production, серверная выкладка, полный release gate и повторный реальный review → dialogue находятся вне объёма. Приёмка использует только синтетические данные.
- Подробности запуска и диагностические артефакты остаются локальными; материалы заказчиков не копируются в технический репозиторий.
