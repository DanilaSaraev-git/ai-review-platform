# Feature Specification: Гостевой доступ без регистрации

Дата: 2026-09-06. Статус: реализовано и развёрнуто, инженерная приёмка завершена по [tasks.md](tasks.md). Основание — запрос пользователя открыть сервис для любого посетителя без кода и сохранить его данные; пользователь выбрал возвращение в том же браузере и одобрил план реализации. Release `3a0ab32c90f6e2aaf5b69e99b1875105761a2b3e`, фактические проверки и их границы записаны в [evidence.md](evidence.md).

## Пользовательские сценарии

### US1 — Открыть сервис и вернуться к своим данным

Посетитель открывает основной адрес через HTTPS, загружает документ, получает проверку, обсуждает замечание и сохраняет решение. Регистрация и ввод кода не требуются.

- Given новый браузер, when открыт основной интерфейс, then создаётся пустое личное пространство с постоянной cookie.
- Given действующая cookie, when страница обновлена или API перезапущен, then доступны прежние документы, профили, проверки, диалоги и решения.
- Given другой браузер или удалённая/истёкшая cookie, when открыт интерфейс, then создаётся новое пространство; прежние серверные данные не удаляются.

### US2 — Сохранить приватность документов

- Given два гостя, when они одновременно работают, then каждый видит и изменяет только своё пространство, включая контекстные документы и пользовательские профили.
- Given чужой или прежний private workspace/resource ID, when гость подставляет его в URL или тело, then данные не раскрываются и изменения отвергаются.
- Given недействующая cookie, when вызвана workspace-операция, then возвращается 401; bootstrap может создать новую сессию.
- Given подготовленный `/demo`, when посетитель открывает его без прежнего gateway-допуска, then приватный пакет недоступен.

### US3 — Продолжить работу после отмены и перезапуска

- Given принятая проверка или реплика, when HTTP waiter отключился, then фоновая операция продолжает работать в своём пространстве.
- Given перезапуск процесса, when приложение стартует, then опубликованные данные остаются, а прерванные операции во всех зарегистрированных пространствах получают терминальную ошибку с допустимым повтором.
- Given несколько гостей, when модель занята, then общий лимит model calls не умножается на число гостей.

### US4 — Ограничить новые загрузки

При достижении [личной или общей квоты](../../contracts/review-platform/guest-v1/README.md#хранение-и-лимиты) новая загрузка получает понятный отказ. Уже сохранённые файлы и история остаются доступными. Проверка квоты учитывает конкурентные загрузки.

## Требования

| ID | Проверяемое требование |
| --- | --- |
| FR-001 | Trusted v1 остаётся режимом по умолчанию; guest-v1 включается явной настройкой API и gateway |
| FR-002 | Cookie хранит случайный непрозрачный credential; PostgreSQL хранит его хеш и связь с workspace/actor |
| FR-003 | Middleware выбирает отдельный platform/runtime по проверенной сессии; общие mutable поля не переключаются между запросами |
| FR-004 | При обходе маршрутов, вложенных source/profile ссылок и download не раскрываются данные другого гостя или прежней группы |
| FR-005 | Данные сохраняются в PostgreSQL/POSIX; cookie продлевается на 30 дней; автоматического удаления данных нет |
| FR-006 | Registry ограничивает число живых runtime, освобождает idle contexts и сохраняет общие client/semaphore |
| FR-007 | Deployment lock единственный; startup reconciliation охватывает исходное и все зарегистрированные гостевые пространства |
| FR-008 | Gateway оставляет `/demo` приватным и прекращает публичный доступ при выключенном гостевом режиме API |
| FR-009 | Гостевой контракт версионируется отдельно; canonical trusted-v1 OpenAPI, предметные DTO и skill JSON не меняются |
| FR-010 | Новые загрузки ограничены размером файла, личной/общей квотой и резервом диска; чтение сохранённых данных работает при отказе загрузки |

## Границы

Аккаунты, роли, доступ с другого браузера, перенос или восстановление сессии, совместные пространства, multi-organization runtime, TTL-удаление файлов и новая модель не входят в этот срез. Качество AI-ревью и экономия времени не выводятся из инженерных тестов.

## Критерий завершения

Synthetic сценарий двух гостей проходит bootstrap → upload → review → dialogue → decision → restart без смешения данных; негативные пути и квоты проверены. Контракт и gateway gates проходят. Реальный выпуск подтверждён отдельными проверками HTTPS-доступа без кода, приватности демо, сохранности гостевой identity/файла после перезапуска и изолированного восстановления. UI production release проверен браузером через приватный SSH-туннель, внешний HTTPS — отдельным curl; прямой browser HTTPS ограничен локальной проблемой соединения. Подробности находятся в evidence.
