# Phase 0. Research: веб-интерфейс AI Review v1

**Дата**: 2026-09-04. **План**: [plan.md](plan.md). **Спецификация**: [spec.md](spec.md).

Стек зафиксирован поручением пользователя и источниками контракта, поэтому исследование не выбирает технологии заново. Оно разрешает оставшиеся неизвестные и фиксирует способ применения каждой выбранной технологии к требованиям спецификации.

## R-01. Точные версии пакетов, не названных числом

**Decision**: точные версии Tailwind CSS 4.x, Radix UI primitives, React Hook Form, Zod, PDF.js, Vitest, Testing Library и Playwright определяются в момент первой установки и немедленно записываются в `package.json` как точные значения без диапазонов, вместе с `package-lock.json`. В плане и задачах эти номера не выдумываются.

**Rationale**: требование пользователя — точные версии без диапазонов; при этом номер, не проверенный установкой, был бы вымышленным фактом. Установка разрешает его один раз, lock-файл делает результат воспроизводимым. Пакеты с явно названной версией (TypeScript 6.0.3, Node.js 24.20.0, React 19.2.8, Vite 8.2.2, React Router 7.18.3, TanStack Query 5.102.8, Orval 8.28.1, MSW 2.15.0) фиксируются ровно этими значениями.

**Alternatives considered**: указать предполагаемые номера в плане — отклонено как непроверенное утверждение; разрешить диапазоны `^` для неназванных пакетов — отклонено, противоречит требованию точных версий.

## R-02. Наблюдение за фоновым запуском при пороге видимости 2 секунды

**Decision**: наблюдение строится на опросе через TanStack Query с интервалом 2000 мс, включённым только для нетерминальных состояний запуска (`queued`, `preparing`, `reviewing`, `validating`) и нетерминальных состояний диалога (`generating`, ход в состоянии `queued` или `generating`). При достижении терминального состояния интервал выключается. Опрос продолжается в фоновой вкладке отключённым, при возврате фокуса выполняется немедленное обновление.

**Rationale**: контракт задаёт `GET /review-runs/{runId}` как ресурс для polling и не предоставляет server-push. Интервал 2000 мс обеспечивает SC-012 напрямую: видимость изменения не позднее 2 секунд. Отключение опроса на терминальном состоянии убирает бессмысленную нагрузку при одном рабочем месте.

**Alternatives considered**: SSE или WebSocket — отклонено, отсутствует в контракте v1, добавление потребовало бы контрактного PR; единый интервал для всех запросов независимо от состояния — отклонено, создаёт постоянный трафик по завершённым запускам; экспоненциальное замедление интервала — отклонено, нарушает порог 2 секунд.

## R-03. Порог «запуск идёт дольше обычного»

**Decision**: признак застревания вычисляется на клиенте как отсутствие смены `state` и `progress` в течение 15 минут, отсчитываемых от `started_at` либо от момента последней замеченной смены. Достижение порога добавляет предупреждение и показ длительности, но не меняет состояние запуска и не прекращает опрос.

**Rationale**: FR-039 и SC-013 требуют наблюдаемого поведения, а контракт не содержит поля «застрял». Вычисление на клиенте не требует изменения контракта и остаётся честным: предупреждение описывает наблюдение интерфейса, а не состояние сервиса.

**Alternatives considered**: добавить в контракт поле таймаута — отклонено, контракт заморожен; автоматически отменять запуск по порогу — отклонено, отмена вне объёма v1 и решение о прекращении принадлежит человеку.

## R-04. Генерация клиента Orval и запрет ручных DTO

**Decision**: `orval.config.ts` в `apps/web/` читает `contracts/review-platform/v1/openapi.yaml` и генерирует в `src/api/generated/` три выхода: типы и fetch-клиент через собственный mutator, query hooks для TanStack Query, MSW handlers. Каталог `src/api/generated/` внесён в `.gitignore`; генерация выполняется скриптом `npm run api:generate` перед сборкой, тестами и в CI, где дополнительно проверяется отсутствие diff после перегенерации. Прикладной код импортирует только из `src/api/generated/` и `src/api/http-client.ts`.

**Rationale**: прямое следствие принципа II. Один источник генерации исключает расхождение типов web и backend; проверка diff в CI ловит попытку править сгенерированный файл руками.

**Alternatives considered**: коммитить сгенерированные файлы — отклонено, принцип II запрещает до отдельного решения команды; писать типы вручную по документации — отклонено, прямое нарушение принципа II; генерировать из экспортированной схемы backend — отклонено, канонический источник — design-first `openapi.yaml`.

## R-05. Идемпотентность создающих операций

**Decision**: mutator в `src/api/http-client.ts` добавляет заголовок `Idempotency-Key` для `createReviewRun`, `createFindingDialogueTurn` и `retryFindingDialogueTurn`. Ключ вырабатывается один раз на намерение пользователя — на форму запуска с конкретным набором входов и на конкретный отправляемый ход — и переиспользуется при повторной отправке того же намерения, включая автоматический повтор после сетевой ошибки. Новый ключ создаётся только при изменении содержимого запроса.

**Rationale**: FR-012 и SC-009 требуют, чтобы повторное нажатие не создавало второй запуск. Контракт делает заголовок обязательным и определяет: тот же ключ и то же тело воспроизводят исходный результат, тот же ключ с другим телом даёт `409`. Привязка ключа к намерению, а не к каждому вызову, реализует это требование без блокировки кнопки как единственной защиты.

**Alternatives considered**: только блокировка кнопки на время запроса — отклонено, не защищает от повторной отправки после разрыва связи; новый ключ на каждый вызов — отклонено, потеряет смысл идемпотентности.

## R-06. Разделение неизменяемого отчёта и изменяемых состояний

**Decision**: отчёт (`GET .../report`) и состояния замечаний (`GET .../finding-states`), а также диалог замечания (`GET .../dialogue`) хранятся в раздельных ключах кэша. Мутации решения и хода диалога инвалидируют только ключи `finding-states` и `dialogue` соответствующего запуска и замечания. Ключ отчёта не инвалидируется ни одной мутацией и считается неизменяемым на всё время жизни запуска: `staleTime` бесконечный, повторная загрузка допускается только при первом открытии или явной перезагрузке страницы.

**Rationale**: принцип V и FR-018, FR-037 требуют, чтобы решения и диалог не меняли отчёт. Раздельные кэши делают это свойством архитектуры данных, а не дисциплиной разработчика: инвалидация отчёта попросту не вызывается. Наложение решений на список замечаний выполняется в представлении по `finding_id`.

**Alternatives considered**: единый агрегированный кэш «отчёт с решениями» — отклонено, стирает границу между неизменяемым и изменяемым и провоцирует перезапрос отчёта после каждого решения; хранение решений в состоянии компонента — отклонено, теряется при переходе и не переживает обновление страницы.

## R-07. Оптимистическая конкуренция и сохранение ввода при конфликте

**Decision**: формы решения и отправки хода держат `expected_revision`, полученную вместе с текущими данными. Ответ `409` с `code: revision_conflict` обрабатывается не как ошибка формы, а как отдельное состояние: интерфейс перезагружает актуальные решение или диалог, показывает актуальное значение рядом с введённым, оставляет введённый текст в полях нетронутым и предлагает повторить сохранение одним действием уже с новой ревизией. Черновик ввода живёт в состоянии формы и не сбрасывается при перезагрузке данных.

**Rationale**: FR-027, FR-036 и SC-005 требуют нулевой потери пользовательского ввода. Стандартный сброс формы после неудачной мутации потерял бы обоснование или текст вопроса, поэтому обработка конфликта выделяется в явный сценарий.

**Alternatives considered**: автоматически повторять запрос с новой ревизией — отклонено, молча затирает чужое решение и нарушает смысл оптимистической конкуренции; показывать общий баннер ошибки — отклонено, не даёт аналитику увидеть расхождение и повторить действие осознанно.

## R-08. Доступность отправки следующего хода диалога

**Decision**: доступность отправки определяется исключительно серверным полем `can_send_message`; клиент не выводит её самостоятельно из числа ходов или состояния. Значение `blocked_reason` отображается человекочитаемым текстом для каждого варианта: `generation_in_progress`, `turn_limit_reached`, `human_decision_recorded`, `dialogue_not_supported`, `model_unavailable`. Неактивный элемент отправки всегда сопровождается причиной.

**Rationale**: принцип V и FR-031, FR-032 требуют не более одного одновременного хода и явной причины недоступности. Контракт называет `can_send_message` вычисляемым на сервере, поэтому дублирование логики на клиенте создало бы расхождение.

**Alternatives considered**: считать доступность на клиенте по состоянию последнего хода — отклонено, расходится с серверными правилами политики диалога; просто отключать кнопку без пояснения — отклонено, прямо запрещено FR-032.

## R-09. Просмотр документа и переход к процитированному фрагменту

**Decision**: используются два представления исходного документа за общим интерфейсом. Для `media_type: application/pdf` — PDF.js: страница из `PdfLocation.page`, подсветка по `rects` в нормализованных координатах `[0..1]`, пересчитываемых в координаты отрисованной страницы. Для `text/markdown` и `text/plain` — текстовое представление с адресацией по `TextLocation` (строки и символы). Байты берутся из `GET .../documents/{documentId}/content`. Если фрагмент не удаётся сопоставить — например, замечание вида `missing` не имеет привязок и содержит только `scope`, либо цитата не найдена в отрисованном фрагменте — интерфейс показывает замечание и явное сообщение о несопоставленном фрагменте, не подсвечивая произвольное место.

**Rationale**: FR-021 и SC-003 требуют перехода к фрагменту либо явного сообщения о неудаче сопоставления. Контракт различает `PdfLocation` и `TextLocation` через дискриминатор `kind`, а для `kind: missing` допускает пустой массив `anchors`, поэтому случай «замечание без привязки» является штатным, а не ошибкой.

**Alternatives considered**: серверный рендер фрагмента в изображение — отклонено, отсутствует в контракте; подсветка по поиску текста цитаты вместо координат — отклонено, при повторяющемся тексте подсветит не то место; единый просмотрщик только для текста — отклонено, PDF является поддерживаемым форматом и основным для реальных ТЗ.

## R-10. MSW и независимость от backend

**Decision**: MSW собирается из сгенерированных Orval handlers, поверх которых лежат именованные сценарии в `src/mocks/scenarios/`, отвечающие каноническими примерами из `contracts/review-platform/v1/examples/http/`. Сценарий выбирается переменной окружения при запуске dev-сервера и параметром запуска в Playwright. Прикладной код о существовании MSW не знает: переключение на реальный backend меняет только базовый URL и отключение worker, но не компоненты и не hooks.

**Rationale**: принцип III требует проверяемости web без backend и запрещает ветвление логики UI по источнику данных. Именованные сценарии дают воспроизводимые негативные случаи: `failed`, частичный отчёт, конфликт ревизии, ход в генерации, недоступная модель.

**Alternatives considered**: собственный mock-сервер с ручными ответами — отклонено, разойдётся с каноническими примерами; флаг «мок или реальный API» внутри компонентов — отклонено, прямое нарушение принципа III.

## R-11. Обработка ошибок и граница доверенного deployment

**Decision**: все не-2xx ответы разбираются как `application/problem+json` в одном месте — mutator клиента — и приводятся к внутреннему типу ошибки с полями `code`, `title`, `detail`, `status`, `request_id`. Отображение выбирается по `code`, а не по тексту. Ответ `404` формулируется как «не найдено», без слов о доступе, входе и правах. `409` различается по `code`: конфликт ревизии, повтор идемпотентного ключа с другим телом, отчёт ещё не опубликован. Значения секретов провайдера модели в интерфейсе не показываются: из `ModelExecution` отображаются только провайдер, модель, версия и безопасные параметры.

**Rationale**: принцип IV и FR-003, FR-004. `workspaceId` в URL — namespace, а не доказательство доступа, поэтому чужой идентификатор обязан выглядеть как обычное отсутствие ресурса.

**Alternatives considered**: показывать `detail` из ответа как единственный текст ошибки — отклонено, серверная формулировка может не подходить экрану и не различает случаи; трактовать `404` как «нет доступа» — отклонено, прямо противоречит границе развёртывания.

## R-12. Доступность интерфейса на базовом уровне

**Decision**: интерактивные элементы строятся на Radix UI primitives, которые дают управление с клавиатуры, корректный фокус и семантику для модальных окон, меню и полей. Каждое поле формы получает видимую подпись, связанную с элементом. Состояния запуска, замечания, решения и хода диалога кодируются текстом либо знаком дополнительно к цвету. Порядок фокуса следует порядку сценария; после отправки хода и после конфликта ревизии фокус переводится на изменившуюся область.

**Rationale**: FR-041, FR-042 и SC-014 требуют прохождения всего сценария с клавиатуры и различимости состояний не только цветом. Radix закрывает механику фокуса и ролей, оставляя на реализацию подписи, текстовые метки состояний и порядок фокуса.

**Alternatives considered**: собственные компоненты диалогов и меню — отклонено, воспроизведение ловушки фокуса и клавиатурной навигации дороже и рискованнее; полное соответствие внешнему стандарту доступности — отклонено, вне объёма v1 по решению из раздела Clarifications спецификации.

## R-13. Объём отчёта и поведение списка замечаний

**Decision**: контракт ограничивает отчёт 500 замечаниями (`ReviewReport.findings`, `maxItems: 500`), и это принимается как технический потолок v1. Список замечаний рендерится целиком, без постраничной выдачи и без виртуализации; порядок берётся из `ordinal` и не зависит от решений и диалога. Сортировка и фильтрация допускаются как представление и не изменяют состав списка. Решение о виртуализации откладывается до первых реальных прогонов.

**Rationale**: спецификация сознательно не задаёт числовую цель по объёму (раздел Clarifications), но контракт даёт верхнюю границу, поэтому «неизвестный объём» не является неопределённостью реализации. Преждевременная виртуализация усложнила бы клавиатурную навигацию и переход к замечанию по ссылке.

**Alternatives considered**: сразу вводить виртуализацию списка — отклонено как усложнение без измеренной потребности и с риском для доступности; постраничная выдача замечаний — отклонено, отчёт приходит одним ресурсом и разбивать его на страницы искусственно незачем.

## R-14. Локаль и формат представления

**Decision**: язык интерфейса — русский; `locale: "ru-RU"` передаётся при создании запуска, как в каноническом примере. Даты и длительности отображаются в локали браузера пользователя с явным указанием часового пояса там, где значение имеет смысл во времени: время создания запуска, время решения, длительность выполнения. Идентификаторы, отпечатки и версии показываются без перевода.

**Rationale**: спецификация фиксирует русский язык результатов и интерфейса. Контракт передаёт время в UTC RFC 3339, поэтому отображение обязано быть явным, чтобы аналитик не спутал момент решения.

**Alternatives considered**: жёстко закрепить московский часовой пояс — отклонено, не следует из требований; показывать сырые значения UTC — отклонено, ухудшает читаемость без выигрыша.

## Открытых вопросов не осталось

Все пункты Technical Context разрешены. Отложенные решения зафиксированы явно и не блокируют реализацию: числовая цель по объёму разбора (R-13) и полное соответствие внешнему стандарту доступности (R-12) вынесены за границы v1 решением из раздела Clarifications спецификации.
