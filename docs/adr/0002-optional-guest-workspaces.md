# ADR-0002: Опциональный гостевой доступ с отдельными пространствами

- Статус: accepted; основание — одобренный пользователем план гостевого доступа от 2026-09-06.
- Область: [срез 008](../../specs/008-guest-access/spec.md), [guest-v1 1.0.0](../../contracts/review-platform/guest-v1/README.md).
- Заменяет в [ADR-0001](0001-contract-first-modular-monolith.md) ограничение одного configured workspace для гостевой поставки. Trusted v1 остаётся режимом по умолчанию.

## Контекст

Посетитель должен открыть сервис без регистрации и кода, проверить документ и позднее вернуться к своим данным в том же браузере. Существующий MVP рассчитан на одну доверенную группу: общий actor/workspace и внешний gateway. Простое снятие gateway-допуска раскрыло бы общие документы.

PostgreSQL-запросы, составные связи, идемпотентность и POSIX-артефакты уже используют workspace. При этом LLM runtime привязан к одному platform и владеет асинхронными задачами; его поля нельзя переставлять между конкурентными запросами.

## Решение

1. `REVIEW_GUEST_ACCESS=false` сохраняет trusted v1. При включённом guest-v1 bootstrap создаёт или восстанавливает постоянную cookie; БД связывает её хеш с отдельными workspace/actor.
2. Middleware выбирает request-scoped platform/runtime только из проверенной серверной сессии. ID из URL не является credential; исходное настроенное пространство и пространства других гостей недоступны.
3. Данные остаются в PostgreSQL и POSIX volume. Истечение или удаление cookie прекращает браузерный доступ, но не удаляет файлы. Аккаунтов и восстановления по email в этом срезе нет.
4. `GuestContextRegistry` создаёт отдельную неизменяемую привязку platform/runtime и task owner. Все контексты заимствуют общий model adapter/client и semaphore. После последнего запроса контекст живёт до завершения фоновой работы, затем освобождает память; число живых контекстов ограничено.
5. Родитель единолично владеет deployment lock и model client. На старте под этим lock выполняется reconciliation исходного и всех зарегистрированных гостевых пространств, включая сессии с истёкшим сроком.
6. Новый вариант границы доступа опубликован отдельным контрактом guest-v1 1.0.0. Пути и формы предметных DTO заимствуются из trusted v1; исходный no-auth OpenAPI не меняется.
7. Gateway открывает основной сервис только при подтверждённом гостевом режиме API. Подготовленные материалы `/demo` остаются за прежним допуском. Cookie и запросы ограничены одним origin; загрузки ограничены [квотами контракта](../../contracts/review-platform/guest-v1/README.md#хранение-и-лимиты).

## Рассмотренные варианты

| Вариант | Решение и причина |
| --- | --- |
| Один общий workspace с owner-фильтрами | Отклонён: нужны новые проверки во всех списках, чтении, загрузках, ссылках контекста, профилях и идемпотентности; выше риск пропустить путь доступа |
| Workspace/actor через ContextVar в общем runtime | Отклонён: скрытый контекст безопасности должен без ошибок проходить HTTP, thread pool и фоновые задачи; отдельные экземпляры делают границу явной |
| Runtime на каждый HTTP request | Отклонён: отмена запроса не должна отменять принятую проверку; task group обязан открываться и закрываться своим owner |
| Регистрация или персональный код | Не выбран пользователем для этого сценария; доступ с другого браузера потребует будущего решения |

## Последствия и границы

Существующие workspace-фильтры используются вместе с проверкой сессии; ID и actor сами не становятся механизмом аутентификации. Не вводятся организации с независимыми администраторами, роли, совместный доступ или OIDC.

Цена решения — отдельный runtime на активного гостя и повторное создание после простоя. Общие лимиты модели не умножаются на гостей. Квоты исходных загрузок не являются верхней границей размера БД, отчётов и журналов.

Переход к нескольким API-процессам, восстановлению аккаунта, длительному хранению с автоматическим удалением или совместной работе требует отдельного решения. Статус проверок и выпуска: [evidence](../../specs/008-guest-access/evidence.md).
